# PitView
#### Video Demo: <[URL HERE](https://youtu.be/rHIyymJQ_-8)>
#### Description:
 
PitView is a real-time telemetry dashboard built as my CS50x final project. It simulates the kind of data a motorsport engineer would monitor during a session — brake pressure, throttle position, and steering angle — and displays them as live updating charts in the browser. Sessions can be recorded to a database and replayed afterwards. There is also an anomaly detection system that flags simultaneous full brake and full throttle inputs, which should not happen in normal driving.
 
The project runs on a Python Flask backend with a SQLite database. The frontend uses Chart.js for the charts and Server-Sent Events to receive live data from the server without polling. A simulated data engine generates realistic telemetry by default, with the architecture designed so that real hardware input from an Arduino Uno can be swapped in later without changing any other part of the codebase.
 
## Files
 
### `app.py`
 
The Flask application entry point. It creates the app instance, registers the three blueprints (dashboard, sessions, auth), calls `init_db()` to set up the database on startup, and sets the secret key from `config.py`. It also contains the `before_request` guard that checks whether the user is logged in before allowing access to any route. Unauthenticated requests are redirected to the login page. The app runs with `threaded=True` so that the Server-Sent Events connection does not block other requests.
 
### `config.py`
 
Stores the application's configuration — the Flask secret key used to sign session cookies, the username, and the hashed password. The password is stored as a `pbkdf2:sha256` hash generated by Werkzeug, not plain text. This means the config file does not expose the actual password even if read directly.
 
### `telemetry/simulator.py`
 
Contains the `Simulator` class, which generates fake telemetry data. Each call to `get_reading()` nudges the current brake, throttle, and steering values by a small random amount using a random walk approach, then clamps the result to its valid range. Throttle and brake are clamped to 0.0–1.0, steering to -1.0 to 1.0. This produces smooth, realistic-looking chart movement rather than the static noise that pure random values would produce. The method `_step()` handles the nudge and clamping for a single channel and is called three times per reading.
 
### `telemetry/source.py`
 
The abstraction layer between the data producers and the rest of the application. It creates a single `Simulator` instance at module level and exposes one function: `get_reading()`. Every part of the app that needs telemetry data imports from here. This means the dashboard, recorder, and anomaly detector are all reading from the same source, and swapping to Arduino hardware later only requires changing this one file.
 
### `telemetry/anomaly.py`
 
Contains `detect_anomaly(reading)`, which takes a reading dictionary and returns `True` if both brake and throttle exceed the threshold of 0.8 simultaneously. This condition — sometimes called a brake/throttle conflict — should not occur in normal driving and indicates either a simulator anomaly or a driver error. The threshold is stored as a module-level variable so it can be adjusted easily.
 
### `database/models.py`
 
Handles database initialisation. The `init_db()` function connects to `pitview.db` and creates two tables if they do not already exist: `sessions`, which stores a timestamp for each recording session, and `readings`, which stores individual telemetry readings linked to a session by foreign key. This function is called once when the app starts.
 
### `database/recorder.py`
 
Manages session recording. It holds two module-level variables — `_recording` (a boolean) and `_current_session_id` — that track whether a session is active. `start_session()` inserts a new row into the sessions table and saves the returned ID. `stop_session()` resets both variables. `record_reading(reading)` writes a telemetry reading to the readings table, but only when `_recording` is True. `get_all_sessions()` returns all sessions ordered by most recent first. `get_session_reading(session_id)` returns all readings for a given session ordered by timestamp, formatted as a list of dictionaries.
 
### `routes/dashboard.py`
 
Contains the live dashboard routes. The `stream()` generator function runs in an infinite loop, calling `get_reading()`, flagging anomalies, calling `record_reading()`, and yielding each reading as a Server-Sent Event. The `/stream` route wraps this generator in a Flask `Response` with the `text/event-stream` MIME type. There are also `/start` and `/stop` POST routes that call `start_session()` and `stop_session()` respectively, triggered by buttons on the dashboard page.
 
### `routes/sessions.py`
 
Contains the replay-related routes. `/sessions` returns a JSON list of all recorded sessions. `/sessions/<id>/readings` returns all readings for a specific session as JSON. `/replay` renders the replay page template.
 
### `routes/auth.py`
 
Handles login and logout. The `/login` route accepts both GET and POST requests. On GET it renders the login form. On POST it checks the submitted credentials against `config.py` using `check_password_hash`, sets `session["logged_in"] = True` on success, and redirects to the dashboard. On failure it re-renders the login page with an error message. The `/logout` route clears the session and redirects to login.
 
### `templates/`
 
Four HTML templates all extending `base.html`. The base template loads Chart.js from a CDN and shows the navigation bar when the user is logged in. `dashboard.html` contains three canvas elements for the live charts, start/stop buttons, and an anomaly warning paragraph. `replay.html` contains three canvas elements, a session dropdown, and play/stop buttons. `login.html` contains the login form with username and password fields and an error display.
 
### `static/js/dashboard.js`
 
Connects to the `/stream` SSE endpoint using the browser's `EventSource` API. Each incoming message is parsed from JSON and pushed onto the relevant data arrays for the three Chart.js charts. A sliding window of 50 data points is maintained by shifting the oldest value off the front of each array when the limit is reached. Charts are updated on every message. If the reading contains `anomaly: true`, a warning message is displayed on the page. The start and stop buttons send POST requests to their respective routes using `fetch()`.
 
### `static/js/replay.js`
 
On page load, fetches the list of sessions from `/sessions` and populates the dropdown with an option for each one, showing the session ID and a formatted timestamp. When the play button is clicked, it fetches all readings for the selected session and steps through them using `setInterval()` at 100ms intervals, updating the three charts with the same push/shift pattern used in the live dashboard. The stop button calls `clearInterval()` to halt playback.
 
## Design decisions
 
The choice to use Server-Sent Events rather than WebSockets came down to simplicity. Data only flows one direction — server to browser — and SSE handles that over a standard HTTP connection with no additional libraries. WebSockets would have added complexity for no benefit in this case.
 
The telemetry abstraction in `source.py` was a deliberate decision made early in the project. Without it, every file that needs data would import `Simulator` directly and create its own instance. That would mean the dashboard and the recorder reading from different objects with different states — a bug that would be hard to catch. Having a single shared instance through `source.py` guarantees everything sees the same data.
 
The random walk in the simulator was chosen over pure random values because pure random produces charts that look like noise, which makes it impossible to spot patterns or test anomaly detection meaningfully. The nudge-and-clamp approach produces values that move like real inputs.
 
## Running the project
 
```
pip install -r requirements.txt
python app.py
```
 
Open `http://localhost:5000`. You will be redirected to the login page. Credentials are set in `config.py`.
